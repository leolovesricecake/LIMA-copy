# LIMA-LLM 优化复盘与后续方案（2026-05-15）

## 1. 结论摘要
- 本次先回退到 `2c933f8` 基线，移除 `deletion_auc/insertion_auc` 与 `gate_b` 相关链路，恢复主线简洁口径。
- 当前评估仍然由推理耗时主导，速度瓶颈未根治。
- `prefetch=on/off` 在同卡同参下仍存在轻微数值漂移，说明“仅调度改动”尚未完全做到数值路径等价。
- 下一阶段应先做“数值等价性收敛”，再做性能优化；否则会持续出现“加速但不可信”的反复。

## 2. 本轮结果复盘（基于你提供的 20 样本 deterministic，同 GPU）

### 2.1 速度
- `prefetch=on`: `runtime_seconds=9506.29`
- `prefetch=off`: `runtime_seconds=8353.26`
- 结果：`on` 比 `off` 慢约 `13.8%`。

### 2.2 指标差异（gold 口径）
- `log_odds`: `0.18121 (on)` vs `0.18225 (off)`，差异 `-0.00104`
- `comprehensiveness`: `0.02554 (on)` vs `0.02112 (off)`，差异 `+0.00442`
- `sufficiency`: `-0.12076 (on)` vs `-0.11696 (off)`，差异 `-0.00380`
- `aopc`: `0.12222 (on)` vs `0.12289 (off)`，差异 `-0.00067`

### 2.3 观察
- 两组 `predict_calls` 都是 `33630`，说明 prefetch 并没有减少“有效前向次数”，主要改变了调度方式。
- 两组 `cache_hit_rate=1.0`，说明缓存逻辑是工作的，差异来自推理路径而非缓存命中。
- `prefetch=on` 在本配置下更慢，说明当前 batch 路径的 padding/调度/实现开销大于吞吐收益。
- on/off 指标不完全一致，意味着 batch 与 single 在数值路径上仍可能存在差异（例如 softmax/精度/张量路径）。

## 3. 迄今为止已做优化（按价值分层）

### 3.1 保留下来的有效优化
- 评估粒度支持 `token/word`，默认 `token`（学术口径对齐）。
- 结果追溯（provenance）完善：commit、分支、dirty、命令参数、环境与 deterministic 状态可审计。
- deterministic 开关与环境记录落地，复现实验链路更清晰。
- 评估阶段已有批量 prefetch 与缓存框架（但性能收益在当前配置下不稳定）。

### 3.2 已确认不稳定/需回退处理的尝试
- 强制 strict 等价路径造成大量“非生产口径”实验，已移除。
- 复杂分桶/重排调度在未做数值一致性证明前引入了漂移风险。
- gate_b 聚合链路在当前阶段不是主目标，已删除。

## 4. 仍然面临的问题
- 问题 A：评估耗时仍极高，`batch_inference` 占比长期接近主导。
- 问题 B：`prefetch=on/off` 不能稳定数值一致，影响可验收性。
- 问题 C：实验对比容易被口径污染（不同设备、脏工作树、旧结果复用等）。
- 问题 D：优化节奏曾跨越过大（多改动同发），导致定位成本高。

## 5. 之后的方案

先做绝对安全的等价优化，包括实现上的减少对象拷贝与构造、调度上的原生python循环等，提高效率。并在结果中记录必要信息，如各个关键环节的时间开销、缓存命中率等等，便于后续分析。

之后再考虑其他可能的优化方案。

如果实在难以优化，可以先扩展到更多数据集与模型、优化子区域划分策略、优化贪心搜索方法、优化子模函数等。
